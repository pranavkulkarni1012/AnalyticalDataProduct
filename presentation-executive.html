System Design

Architecture Overview

A config-driven, SQL-first framework. All transformation logic lives in SQL inside the config. Pipeline code is generic and shared across all data products.

Key Principle

Multiple data products share the same pipeline code. Each product has its own config file containing the SQL query. The generic pipeline reads the config at runtime, executes the SQL against Snowflake, and writes the result to Iceberg.

⚙

Minimal Repository

No pre-existing templates, scripts, or boilerplate checked in. All code generation logic lives in 10 skills and 6 agents under .claude/. Everything is generated on demand.

Soft Fail

Error Handling Strategy

Stages 1–3: Hard Stops

Downstream agents cannot produce meaningful output without structured requirements, production-ready SQL, and a validated config. Pipeline halts immediately on failure.

Stages 4–6: Soft Failures

Code can be regenerated, infrastructure issues are environment-specific, and QA failures indicate data issues. Pipeline continues and reports all issues at the end.

AI Workforce

6 Specialized Subagents

Each agent is an isolated AI subprocess with scoped tool permissions. Agents are spawned in sequence by the /run-sdlc orchestrator, each in its own clean context.

1

Requirement Parser

Stage 1 · Hard Stop on Failure

Reads a Jira ticket via Atlassian MCP and extracts a structured requirement object with draft SQL, source tables, runtime parameters, and target definition.

  • Fetches ticket title, description, acceptance criteria, labels
  • Identifies source tables with fully-qualified names
  • Drafts suggested_sql with CTEs and aggregations
  • Extracts runtime filter parameters (${param_name} placeholders)
  • Posts extraction summary comment back to Jira
Tools: Atlassian MCP (getJiraIssue, addComment)  |  Input: Jira ticket key  |  Output: 01-requirements.json
2

Spec Generator

Stage 2 · Hard Stop on Failure

Refines draft requirements into a production-ready technical specification with polished SQL, then publishes to Confluence and links it on the Jira ticket.

  • Fully-qualifies all table names with double-quoted identifiers
  • Structures SQL as CTEs for clarity and maintainability
  • Selects compute engine (Glue default, or Lambda/ECS/EMR)
  • Defines reconciliation rules and runtime parameters
  • Publishes formatted spec to Confluence
Tools: Atlassian MCP (Confluence + Jira)  |  Input: 01-requirements.json  |  Output: 02-spec.json + Confluence page
3

Config Generator

Stage 3 · Hard Stop on Failure

Transforms the technical spec into a validated pipeline config YAML with engine-specific defaults, SQL-driven transformations, and auto-fix retries on validation failure.

  • Maps spec into YAML with 8 sections (7 required + parameters optional)
  • Applies engine-specific defaults (Glue: G.2X/10 workers; Lambda: 3008 MB)
  • Validates via /validate-config with up to 3 auto-fix attempts
  • Validates Snowflake connection via /validate-connection
Skills: /validate-config, /validate-connection  |  Input: 02-spec.json  |  Output: 03-config.yaml
4

Pipeline Generator

Stage 4 · Continues on Failure

Deploys the generic shared pipeline for the compute engine, generates Step Function orchestration, and produces pytest test stubs with flake8 + bandit linting.

  • Invokes /generate-pipeline which delegates to engine-specific skills
  • Invokes /generate-step-function for ASL orchestration JSON
  • Generates pytest stubs (config integrity, SQL validation, recon tests)
  • Runs flake8 + bandit with up to 3 auto-fix iterations
Skills: /generate-pipeline, /generate-step-function, /generate-{engine}-pipeline  |  Output: pipelines/
5

Infra Agent

Stage 5 · Continues on Failure

Generates Terraform infrastructure-as-code, validates it, and deploys with strict environment-aware controls. Never auto-applies to production.

  • Invokes /generate-terraform for modules (IAM, Step Functions, monitoring, engine)
  • Runs terraform fmt, validate, and plan
  • Dev/staging: Auto-apply if no resource destruction
  • Production: Creates GitHub PR with plan output for human approval
Skills: /generate-terraform  |  Tools: GitHub MCP (PR for prod)  |  Output: terraform/
6

QA Agent

Stage 6 · Continues on Failure

Runs reconciliation and data quality checks, generates a validation report, posts results to Jira, and transitions the ticket based on pass/fail status.

  • Invokes /run-recon for source vs target comparison (4 rule types)
  • Runs data quality checks: not_null, unique, range, regex, custom
  • Posts structured results table to Jira as a comment
  • Transitions ticket: PASS → Done, FAIL → Blocked
Skills: /run-recon, /validate-config  |  Tools: Atlassian MCP (Jira)  |  Output: 06-validation-report.json

Compute Layer

Four Compute Engines

One generic pipeline per engine serves all data products. The framework automatically selects the right engine based on workload characteristics.

⚙

AWS Glue

PySpark
Default engine for large-scale ETL. GlueContext + managed Spark. Best for >1 GB datasets.
⚡

AWS EMR

PySpark
Custom Spark configs, GPU workloads. Serverless preferred. Best for >100 GB datasets.
λ

AWS Lambda

Python + Pandas
Lightweight, event-driven transforms. <1 GB, <15 min runtime. No Spark dependency.
▢

AWS ECS

Python + Docker
Long-running Python jobs. No timeout limit. Fargate serverless containers.

Dynamic Execution

Runtime Features

Pipelines are dynamic and environment-aware without modifying pipeline code. Two runtime features enable this.

${}

Runtime Parameters

Pass dynamic filter values at execution time. SQL uses ${param_name} placeholders safely substituted with type-validated, SQL-escaped values.

  • 5 types: string, date, integer, number, boolean
  • Safe: Type validation + SQL escaping — no str.format()
  • Optional: Datasets without parameters work unchanged
  • Consistent: Same substitution in query SQL and reconciliation
ENV

Environment Awareness

Every pipeline knows which environment it runs in (DEV, TEST, PROD). Defaults to DEV locally. Terraform sets it automatically on deployment.

EngineHow ENV Is Set
Glue--ENV in default_arguments
EMR--env via Step Function args
LambdaENV environment variable
ECSENV in container definition
Delivery

CI/CD Workflow

Jenkins handles continuous integration. Harness manages deployment with progressive approval gates across three environments.

CI

Jenkins (Build)

Seven-stage build pipeline with automated quality gates:

  • Checkout — Clone repository
  • Validate Config — Schema validation
  • Lint — flake8 (style) + bandit (security) in parallel
  • Unit Test — pytest with JUnit reporting
  • Terraform Validate — fmt + validate per environment
  • Package — Upload artifacts to S3
  • Terraform Plan — Generate and archive the plan
CD

Harness (Deploy)

Three-stage deployment with escalating approval gates:

StageApprovalAction
DEV None (auto) Apply, trigger Step Function, integration test
STAGING 1 engineer (24h) Apply, reconciliation validation
PROD 2 approvers (48h) Apply, smoke test, Jira update

Production requires data platform lead + product owner approval. Each stage includes automatic rollback on failure.
