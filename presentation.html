Architecture Overview

A config-driven, SQL-first framework where one generic pipeline per compute engine serves all data products. Each product is defined entirely by a YAML config containing the SQL query. No per-product code generation — only the config differs.

Config-Driven

Single YAML file with SQL defines your entire data product. Pipeline code is generic and shared.

SQL-First

All transformation logic (CTEs, joins, aggregations) lives in query.sql inside the config.

Agent-Driven

6 specialized AI agents handle each stage. All code, infra, and tests are generated on demand.

High-Level Flow

Jira Ticket  →  Parsed Requirements  →  Technical Spec + Confluence  →  Pipeline Config (YAML + SQL)
→  Generic Pipeline + Step Function + Terraform  →  CI/CD Build & Deploy  →  Validation & Production Monitoring

Error Handling Strategy

Stages 1–3 are hard stops — downstream agents cannot produce meaningful output without structured requirements, production-ready SQL, and a validated config. Stages 4–6 are soft failures — code can be regenerated, infrastructure issues are often environment-specific, and QA failures indicate data issues rather than pipeline issues.

Subagent Reference

Each agent is a specialized Claude Code subagent (model: claude-opus-4-6) with scoped tool permissions. Agents are spawned in sequence by the /run-sdlc orchestrator.

1
Requirement Parser
Agent

Role: Reads a Jira ticket via Atlassian MCP and extracts a structured requirement object with draft SQL.

  • Fetches ticket title, description, acceptance criteria, labels, and components
  • Identifies source tables with fully-qualified names (DATABASE.SCHEMA.TABLE)
  • Drafts suggested_sql with CTEs, joins, and aggregations
  • Handles missing fields gracefully — sets to null with warnings (never fails)
  • Posts extraction summary comment back to Jira
Input
Jira ticket key (e.g. SCRUM-123)
Output
artifacts/{run_id}/01-requirements.json
2
Spec Generator
Agent

Role: Refines draft requirements into a production-ready technical specification with polished SQL, then publishes to Confluence.

  • Fully-qualifies all table names with double-quoted identifiers
  • Structures SQL as CTEs for clarity and maintainability
  • Defines single source connection (OAuth + proxy), target Iceberg schema, partition spec
  • Selects compute engine (Glue default, or Lambda/ECS/EMR based on workload)
  • Defines reconciliation rules (row_count, sum, distinct_count) with source & target SQL
  • Publishes formatted spec to Confluence and links it on the Jira ticket
Input
01-requirements.json
Output
02-spec.json + Confluence page + Jira comment
3
Config Generator
Agent

Role: Transforms the technical spec into a validated pipeline config YAML with engine-specific defaults and auto-fix retries.

  • Maps spec into YAML with 7 required sections (product, compute, source, query, target, reconciliation, runtime)
  • Applies engine-specific defaults (Glue: G.2X/10 workers; Lambda: 3008 MB; ECS: 2048 CPU; EMR: serverless)
  • Validates against embedded JSON Schema via /validate-config skill (up to 3 auto-fix attempts)
  • Validates Snowflake connection via /validate-connection skill
  • Writes to both artifacts/ and durable configs/ directory
Input
02-spec.json
Output
03-config.yaml + configs/{product_name}.yaml
4
Pipeline Generator
Agent

Role: Deploys the generic shared pipeline for the compute engine, generates Step Function orchestration, and produces test stubs.

  • Invokes /generate-pipeline → deploys generic code to pipelines/generic/{engine}/
  • Invokes /generate-step-function → creates ASL JSON with engine-specific task resource
  • Generates pytest test stubs (config integrity, SQL validation, source/target/recon tests)
  • Runs flake8 + bandit linting with up to 3 auto-fix iterations

Skills used: /generate-pipeline, /generate-step-function, /generate-{glue|emr|lambda|ecs}-pipeline

Input
03-config.yaml
Output
pipelines/generic/{engine}/ + pipelines/{product}/step_functions/ + pipelines/{product}/tests/
5
Infra Agent
Agent

Role: Generates Terraform infrastructure-as-code, validates it, and deploys with strict environment-aware controls.

  • Invokes /generate-terraform → creates modules for IAM, Step Functions, monitoring, engine resources
  • Runs terraform fmt, validate, and plan
  • Non-prod (dev/staging): Auto-apply if no resource destruction
  • Production: NEVER auto-apply — creates GitHub PR with plan output for human approval
  • Generates per-environment configs with scaled-down dev/staging defaults
Input
03-config.yaml + env
Output
terraform/ + plan output + PR (for prod)
6
QA Agent
Agent

Role: Runs reconciliation and data quality checks, generates a validation report, posts results to Jira, and transitions the ticket.

  • Invokes /run-recon → compares source (Snowflake) vs target (Iceberg) metrics
  • Runs data quality checks: not_null, unique, range, regex, custom
  • Generates structured validation report with per-rule results
  • Posts results table to Jira as a comment
  • Transitions Jira ticket: PASS → Done, FAIL → Blocked
Input
03-config.yaml + Jira ticket
Output
06-validation-report.json + Jira comment + ticket transition

Hard Constraints & Guardrails

Non-negotiable rules enforced at multiple layers: CLAUDE.md instructions, hooks, skill validation, and agent logic.

Data Sources

  • ✕ Snowflake is read-only — no INSERT, UPDATE, DELETE, DDL
  • ✓ OAuth authentication only — no passwords, no key-pair
  • ✓ Corporate proxy required when proxy config present
  • ✓ OAuth tokens from AWS Secrets Manager only

Data Targets

  • ✓ Apache Iceberg tables on S3 via Glue Catalog only
  • ✕ No Hive, Delta, or Hudi table formats
  • ✓ Iceberg format-version 2 enforced

Infrastructure

  • ✓ Terraform as sole IaC tool — no CloudFormation, CDK, Pulumi
  • ✓ Separate AWS accounts per environment (dev, staging, prod)
  • ✓ Remote state in S3 + DynamoDB locking

Security & Deployment

  • ✕ No hardcoded credentials, tokens, or secrets
  • ✓ Least-privilege IAM scoped to specific resources
  • ✕ Production: never auto-apply Terraform — always PR with 2 approvals
  • ✓ Jenkins CI + Harness CD mandated
